数据清洗脚本审查总结
=====================
日期：2026-08-09
审查范围：data/scripts/ 下 5 份清洗脚本
审查人：Claude (sdcs13669 复核)


一、总体结论
────────────────

五份脚本结构清晰，缺失值处理和公共特征派生正确。存在一个通病和三处个性问题。


二、通病：路径错误（5/5）
────────────────

ROOT = Path(__file__).resolve().parents[1]   →  <repo>/data/
RAW  = ROOT / "data" / "raw" / "..."        →  <repo>/data/data/raw/   ✗
PROC = ROOT / "data" / "processed"           →  <repo>/data/data/processed/  ✗

脚本位于 data/scripts/ 下，parents[1] 是 data/，再拼 data/... 造成路径重复。
应改为 parents[2]（指向仓库根目录），或改用相对路径。


三、个性问题
────────────────

3.1 clean_steel_ind.py：本地特征完全跳过异常检测 [严重]

仅对 Usage_kWh（目标列）做了 MAD Z + diff spike。lagging_reactive_power、
leading_reactive_power、co2、lagging_pf、leading_pf 五列本地特征完全未做异常检测。
CO2 传感器故障或无功功率突变会原样进入 processed。

对比其他脚本：
  - tetouan_city: 对 3 个 Zone 目标 + 5 个本地特征逐一调 clean_series
  - household_res: 遍历所有数值列调 clean_series
  - lcl_res: 按用户独立调 clean_series
  - steel_ind:  只处理了 Usage_kWh  ← 唯一遗漏

3.2 clean_steel_ind.py：冗余列未剔除

NSM（距午夜秒数）、WeekStatus、Day_of_week 已被公共特征覆盖，
仍保留在输出 CSV 中。


3.6 clean_tetouan_city.py：category_id 常量

所有行 category_id = 1，但 Zone 1 应为 2（工业）、Zone 2/3 应为 0（居民）。
需在建模阶段按客户端覆盖，非清洗脚本层面的问题。

3.7 clean_tetouan_city.py：输出列重复

原始列名（如 "Temperature"、"Zone 1 Power Consumption"）和重命名列
（temperature、load_zone1）同时出现在输出 CSV。

3.8 clean_eld_ind.py：MAD Z 非对称

z > 10 只截高端，与规范 |z| > c 写法不一致。对本数据集（功率无负值）影响小，
但偏离规范。
c 取值 之大难以想象

四、关于物理界检测的结论
────────────────

审查过程中确认：用电数据的物理界无法先验获知（峰值负荷取决于变压器容量、
产线规模等未知因素）。五份脚本中 clip(0, max_val) 的逻辑要么误伤合法高峰、
要么设得足够宽而不触发。正确做法是删除物理界截断，完全依赖 MAD Z + diff spike
做统计异常检测。


五、验证通过的方面
────────────────

- 所有脚本缺失值处理正确（小缺口 ≤6 步插值、大缺口保留 NaN）
- 公共特征派生一致（7 个时间 sin/cos + 1 个 category_id）
- 时间步统一到 1800s（30min），重采样策略正确
- lcl_res 按用户分组处理，符合 FL 隐私约束（不跨客户端）
- eld_ind 向量化按列处理，每列即每客户端
- 断点续跑机制（lcl_res）已实现
