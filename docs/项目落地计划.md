> 版本：v1.1
> 目标读者：项目全体成员
> 定位：从数据采集到系统落地的分阶段路线图

---

## v1 范围界定

- **纳入**：MQTT/HTTPS 通信链路、可控使用（联邦学习 + 差分隐私）、审计日志
- **后期**：可信采集（需硬件支持）、区块链上链、DID 数字身份
- **部署形态**：单机模拟 → Docker Compose 容器路线（满足交付"部署镜像"要求）

## 各阶段详情

### 阶段 1：数据采集与清洗

- 按《完整数据处理管线.md》选数据集、入库 raw → processed
- 写 manifest 与质量报告

### 阶段 2：联邦基线

- 实现 GlobalTCN 点预测模型（PyTorch）
- 按客户端配置切分数据，**基于 Flower (flwr) + Ray 单机仿真**跑 FedAvg 聚合训练 GlobalTCN（不加 ResidualCorrector）
- 模型仅使用 10 个公共特征（时间派生 + category_id 独热编码 + 历史负荷），不引入本地特征
- 产出 `Y_pre` 的 WAPE/MAE 基线
- 基线是后续个性化（Phase 3）的对照靶子：`Y_final vs Y_pre` 的差值直接量化个性化修正的增益

### 阶段 3：联邦模拟 + 个性化（可控使用核心）

- 数据按参与方切分（participant_id）
- FedAvg / FedProx + 共享 TCN 编码器 + 本地个性化头
- 三组对比：本地模型 / 标准 FedAvg / 个性化联邦

### 阶段 4：差分隐私 + 隐私评估（可控使用核心）

- DPSGD：L2 裁剪 + 高斯噪声 + 隐私会计器
- 产出 ε-WAPE、ε-AUC 权衡曲线

### 阶段 5：通信链路 + 审计日志

- 对应fl_code\Federal learning simulation内容
- 采集端用脚本模拟上报（MQTT / HTTPS），不依赖硬件
- 联邦模型更新走 Flower 内置 gRPC 通信（`start_server` / `start_client`），无需自建传输层
- 服务器记录审计日志：参与方在线状态、更新接收、ε 消耗、模型版本
- Docker Compose 编排 **1 server + 3~4 client 容器**，单机快速出结果

> **注：Phase 5  偏向 架构演示，要求可以快速抛出训练结果。** 4 个 client 容器（ steel_ind_0 + tetouan_city 3 个 zone都是1年时长的序列，样本数不会多，本地一轮可能只要十几秒）即可证明联邦通信链路可工作。所有容器共享同一个轻量镜像（PyTorch CPU + Flower，约 1.5 GB），数据文件直接挂载。训练效果已在 Phase 2/3/4 产出，Phase 5 只跑 2~3 轮演示通信逻辑 + 审计日志完整。

## 执行原则

- 阶段 1、2 可并行
- 每阶段产出文档/图，作为答辩材料
- 阶段 5 依赖 3/4 的模拟器；阶段 6 依赖 5
- v1 不做硬件可信采集与区块链上链，需在演示中说明为后续方向
- **核心数据结果来自 Phase 2/3/4**（服务器 GPU 全量训练），Phase 5 仅做通信架构演示

## 技术选型备注

- **联邦框架**：Phase 2 起采用 Flower (flwr) + Ray 单机仿真，替代手写 FedAvg。Flower 自带 FedAvg/FedProx/DP 策略和 gRPC 通信层，Phase 3/4/5 均可复用
- **Phase 5 容器规模**：1 server + 3~4 client 容器即可（演示通信架构，无需 1:1 映射真实客户端数量）。共享镜像（PyTorch CPU + Flower），数据文件挂载
- **仿真 vs 容器**：Phase 2/3/4 使用 Flower Ray 仿真模式（单进程内 actor 模拟多客户端），Phase 5 换为真实 client-server 通信模式。训练代码和模型不变，仅启动方式不同
