> 读者：App 线 3 名大一同学
> 版本：v1.0（2026-08-16）
> 关联文档：设计文档 `docs/superpowers/specs/2026-08-16-fl-app-design.md`、实施计划 `docs/superpowers/plans/2026-08-16-fl-app.md`（两者不在 git 里，由组长单独分发，见 §8）

## 1. 这个 App 是干什么的

一句话：**让多台电脑一起训练一个用电量预测模型，但每台电脑的数据始终留在自己机器上，不出门。**

- 一台电脑"发起"一个联邦学习任务（发起者同时就是服务器）
- 其他电脑凭"地址 + 密钥"加入，各自用**自己本机的电力数据**在本地训练
- 训练完只把模型参数（不是数据！）发给服务器，服务器聚合出全局模型再发回，如此往复多轮
- 隐私保护：客户端上传前对参数做差分隐私（DP）加噪（本地裁剪 + 高斯噪声），服务器永远拿不到任何客户端的原始信息
- 一轮轮结束后：服务器输出最终模型 + 完整日志（谁该来、谁来了、谁掉线）；每台客户端本地输出隐私预算曲线，并可本地训练一个"残差修正器"（个性化，纯本地）
- 最后可视化三张曲线对比：真实用电曲线 vs 只靠联邦全局模型的预测 vs 加了个性化修正器的预测

### 术语速查（写代码/问 AI 时会遇到）

| 术语 | 大白话解释 |
| --- | --- |
| 联邦学习 | 多台机器各用自己的数据训练，只交换模型参数、不交换数据，最后合成一个全局模型 |
| 聚合（FedAvg） | 服务器把各客户端上传的参数按数据量加权平均，得到新的全局模型 |
| 差分隐私（DP） | 给上传的参数加随机噪声，让服务器无法反推任何一个人的数据；ε/δ 是"花了多少隐私预算"的参数，C 是裁剪范数（限制单个样本的影响） |
| 残差修正器（二阶段） | 每台客户端本地训练的小模型，专门修正全局模型在自己数据上的预测误差，纯本地、不上传 |
| flwr / gRPC | flwr（flower）是现成的联邦学习框架，底层用 gRPC 通信协议——App 只调用它，不用自己实现网络协议 |

## 2. 完整功能愿景（最终形态）

### 发起者视角（服务器窗口）

1. 打开 App，在"发起联邦学习"表单里填：任务名、轮次数、开始时间（立即或定时 HH:MM）、每轮等待秒数、DP 参数（目标 ε、δ、裁剪范数 C、本地 epochs、batch 大小）、监听端口
2. 点"生成密钥"→ 得到一行"地址:端口 + 随机密钥"，复制发给朋友（微信/口头）
3. 点"启动服务器"→ 进入等待期：已注册客户端列表实时刷新
4. 到开始时间自动开始训练，每轮显示：应参与名单、实际参与名单、掉线名单、聚合损失曲线
5. 结束后：服务器端得到最终模型 `checkpoints/round_NNN.pt` + 审计日志 `audit_log.json`

### 参与者视角（客户端窗口）

1. 打开 App，在"加入联邦学习"里填：服务器地址、端口、密钥、自己的客户端 ID
2. 私密配置：填写本机数据集路径（只有自己知道，永不上传）
3. 状态变"已就绪，等待开始"→ 到点自动开始本地训练
4. 训练中：当前轮次、本地损失、**隐私预算曲线**（每轮花了多少 ε，逐轮累加）
5. 一阶段结束：收到完成通知
6. 点"本地训练残差修正器"（二阶段，纯本地，不联网）
7. 可视化页：真实 vs 联邦全局预测 vs 个性化预测三条曲线对比

### 简化约定（榜题需求的最简落地）

- "用户登录"：不设账号密码系统，客户端加入时填一个客户端 ID 即可
- "广场"：= 本机任务列表（发起过的任务历史），没有中心服务器、没有自动发现
- 发起者同时就是服务器，省一台物理机

## 3. 关键设计决策（为什么这样）

| 决策 | 结论 | 一句话理由 |
| --- | --- | --- |
| 通信 | flwr（flower）库 `start_server` / `start_client`，gRPC | 现成传输层，不用自己写网络协议；榜题要"软硬件联动可靠" |
| 界面 | tkinter（Python 自带 GUI 库） | 环境已装、仓库有先例（fl_code/visualize_eval.py）、打包成熟 |
| 任务发现 | 密钥 + 地址直连 | 无中心服务器，发起者把"IP:端口 + 密钥"发给参与者即可 |
| 隐私 | DP 在客户端本地做（裁剪 + 加噪后才上传） | 数据不出本机；服务器聚合是"后处理"，即使服务器不可信也保得住隐私 |
| 密钥强度 | 演示级凭证（防误入不防攻击） | 文档如实声明，不做 TLS/认证 |

## 4. 壳子阶段（阶段 A）要实现什么 —— 重点

**目标一句话：做出完整可点的界面，并用 socket 消息证明两台电脑能真实通信。训练、DP、聚合全部用假数据。**

为什么先做壳子：界面框架、消息通道、一键启动这些"软件工程"部分先做完；等实验线把训练核心就绪后直接嵌入（阶段 B），窗口代码基本不用改。

### 4.1 分工

| 同学 | 负责文件 | 产出 |
| --- | --- | --- |
| A | `app/server.py` | 服务器窗口（发起表单 + 密钥 + 已连接列表 + 消息日志） |
| B | `app/client.py` | 客户端窗口（加入表单 + 状态 + 空图占位 + 置灰的二阶段按钮） |
| C | `app/protocol.py` + 启动脚本 + 验收 | TCP 消息通道 + run_server.bat / run_client.bat + 组织双机验收 |

### 4.2 每个文件的要求

**protocol.py（C）**：纯标准库 socket/threading/json。
- `MessageServer(host, port, on_message)`：监听端口，后台线程收消息，回调给窗口
- `MessageClient(server_host, server_port, on_message)`：连接服务器，发/收消息
- 线路协议：每条消息 = 一行 JSON（`json.dumps(msg) + "\n"`，UTF-8）。必须走 TCP socket 而不是 txt 文件——提前验证"IP + 端口"这条网络通路（防火墙放行、局域网可达），这正是将来 flwr 通信也依赖的通路，问题在壳子阶段就暴露出来

**server.py（A）**：可启动的 tkinter 窗口。表单字段：任务名、轮次数、开始时间(HH:MM，空=立即)、每轮等待秒数、DP 目标 ε、DP δ、裁剪范数 C、本地 epochs、batch 大小、监听端口。"生成密钥"按钮（`secrets.token_hex(16)`，显示"地址:端口 + 密钥"供复制）。"启动服务器"按钮（开 MessageServer）。已连接客户端列表。滚动消息日志面板（收到消息逐行显示并回执）。

**client.py（B）**：可启动的 tkinter 窗口。加入表单：服务器地址、端口、密钥、客户端 ID、本地数据路径(私密)。"加入"按钮。状态标签（未连接 / 已连接）。两张空图占位（matplotlib Figure 嵌入）："隐私预算曲线(ε vs 轮次)"、"预测对比：真实 vs 联邦 vs 个性化(占位)"。"本地训练残差修正器(二阶段)"按钮（置灰，阶段 B 启用）。

**run_server.bat / run_client.bat（C）**：双击即启动窗口（Python 路径按各自机器改）。

> 消息的具体字段（hello / ack 的 JSON 结构、回调签名）以计划的 Task 3-5 代码为准，A/B/C 三人实现前先对一遍计划里的 Interfaces。

### 4.3 阶段 A 验收清单（8/31 前，逐项打勾）

在**两台物理机**（或一台机器 + 虚拟机桥接网络）上：

1. 机器 A 双击 run_server.bat → 生成密钥 → 启动 → 日志显示 `服务器已启动: <局域网IP>:8088`（默认端口 8088，两边保持一致即可）
2. 机器 B 双击 run_client.bat → 填机器 A 的局域网 IP / 8088 / 密钥 → 加入
3. 机器 A 日志出现机器 B 的 hello 消息；机器 B 状态变"已连接（收到服务器回执）"
4. 反向再来一遍（在 B 上同样跑 run_server.bat 当服务器，A 当客户端连它）——双向互通
5. 连不上时：检查 Windows 防火墙放行 8088，把排查过程记进部署手册

### 4.4 壳子阶段明确不做的事

- ❌ 不接 flwr、不训练、不做 DP、不碰 `fl_code/fed_core`
- ❌ 不做密钥校验：密钥字段只是收集占位，填什么都允许连接（阶段 B 才有 JOIN/OK/DENY 校验）
- ❌ 本地数据路径字段只是占位收集，不实际读取数据（阶段 B 才真正使用）
- ❌ 二阶段按钮保持置灰；两张图保持空白占位
- ❌ 不打包 exe（提交前的加分项，最后再说）

## 5. 汇合阶段（阶段 B）预告

壳子验收后：把消息通道升级为"注册通道"（JOIN/OK/DENY/START + 密钥哈希校验），再嵌入真实训练——服务器启动 flwr ServerApp、客户端启动 flwr ClientApp，训练/DP/聚合全部来自实验线写好的 `fl_code/fed_core`（接口已冻结，见设计文档 §5.1）。窗口代码基本不动。细节在实施计划的 Task 10-13。

## 6. 与实验线的分工边界

- 实验线已完成：`fl_code/fed_core/`（参数转换、DP 会计、客户端训练、服务器聚合）+ `train_baseline.py` 重写；同一套代码既跑单机仿真又供 App 使用

## 7. 怎么用 AI coding agent 干活

每人配一个 AI 编程助手（Claude Code 等），按下面的方式用：

1. **喂三份材料（顺序）**：① 本说明（理解要做什么）→ ② 实施计划里你自己的 Task（C = Task 3 和 6，A = Task 4，B = Task 5；直接对 agent 说"读 `docs/superpowers/plans/2026-08-16-fl-app.md` 的 Task N，按步骤执行"）→ ③ 设计文档（有疑问时查"为什么"）。**先让组长把这两个文件发到你的机器上**（§8 有说明）
2. **让 agent 严格按计划步骤执行**：每个 Task 都是"先写测试 → 跑测试确认失败 → 写实现 → 跑测试确认通过 → 提交"，让它一步步来，别跳步、别自由发挥。界面细节（比如 matplotlib 嵌进 tkinter 的 FigureCanvasTkAgg）计划里给了完整代码，让 agent 照抄即可。测试文件放 `tests/` 目录（仓库已有），按计划里给的文件名新建
3. **验收**：`pytest tests/` 全绿 + 手动按 §4.3 清单点一遍界面
4. **铁律**（计划的 Global Constraints 里也有）：
   - 冒烟/验证运行必须把输出指到 `C:/tmp` 临时目录，**严禁写正式产物目录**（fl_code/baseline_outputs、personalized_outputs、figures）
   - 控制台打印只用 GBK 安全字符（Windows 控制台），禁用下标字符（σᵢ 等）
   - Python 用 `D:\anoconda\envs\fl\python.exe`
   - 提交前 `git status` 检查，别把 app/runs/ 等运行产物提交进去
